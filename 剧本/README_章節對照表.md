5. **錨點章不動。** §六登記的硬錨點（登場與入隊章、分支節點與回收章、遺物取得章、劇透閘門、章號ID）所在章號不得改變。幕界章由規則3保護；**幕內錨點**只在拆分與抵銷合併位於它同一側時不動——拆在前、併在後（或反過來），夾在中間的錨點都會偏移一章。被拆章與被併兩章本身也要檢查：拆在前時，被拆章的後半與被併兩章中的前一章會移動；併在前時，被併兩章中的後一章與被拆章的前半會移動。§五各列的默認排法一律錨點安全；會移動錨點的排法只寫成「可選（需核可）」。確實必須移動時：先經作者核可，再按§六列出全部依賴引用（含99副本、遊戲數據、ID名），同一提交更新。
6. **命名空間。** 正式腳本ID與遊戲數據（`CHnnn_…`、`FI_／FLAG_／SAVE_／BATTLE_CHnnn_…`、遊戲 `chNNN`、`index.json`）一律跟正式章號；正式章號上線後不重編（進度與存檔以章ID為鍵，遊戲 `public/story/player.js:15–19`）。總綱示例ID（如 `CH001_WHEAT_SEVEN_SPARKS`，設12:85）屬總綱命名空間，不得再作正式ID。正式06–08與各幕界章同號；其餘幕內章在§五默認排法下同號（第五幕A、B除外），採可選排法時以§五為準；引用舊文件時一律標明命名空間。設定集裡以章號命名或比較章號的機制（`BR_CHnnn_`、`FLAG_MAIN_CHnnn_`、`PROMISE_CHnnn_`、`spoiler_ceiling`、`made_chapter`、`chapter` 字段）按正式章號解讀（擴展解釋，待作者確認，見附5）。

## 七、維護流程

**規劃一章時**

- [ ] 在§五找到對應總綱章，讀錨點欄（含BR回收點與軟錨點）；第一幕讀§四；查§三，把待回收落點寫進章前備註。
- [ ] 確認不越過本幕幕界；10分鐘評估超出時按「移位時」或「拆分時」處理。
- [ ] 腳本ID、旗標、存檔名用正式章號；不得沿用總綱示例ID。
- [ ] 寫完或核可後，同一提交：更新§二或§五狀態、勾銷§三回收項、更新 `README_劇本編寫規格.md` §五；遊戲上線時同步 `index.json` 與上一章 `end.next`。

**移位時**（節拍跨章移動，章數不變）

- [ ] 在來源章與接收章的§五備註（第一幕為§四）同時登記。
- [ ] 按接收章的評估重算；超過1.2時先刪接收章的可壓項，不得把超時再推給下一章。
- [ ] 移位不得越過幕界，也不得把錨點內容（登場、分支節點、回收點）移出其錨點章。

**拆分時**

- [ ] 在同一幕指定抵銷的合併章，寫進該幕平衡行。
- [ ] 檢查拆分與合併之間是否夾著錨點，含被拆章與被併兩章本身會移動的那一半或那一章（規則5；§五錨點欄、§六）；有就改排序，或走「錨點必須移動時」。
- [ ] 不切斷同一個完整衝突（規:39）。

**合併時**

- [ ] 被併章的錨點內容（登場、分支節點、回收點、伏筆）在合併章中仍要出現。
- [ ] §五保留被併總綱章的列，「預定正式章」填合併後章號。

**錨點必須移動時**

- [ ] 先經作者核可。
- [ ] 按§六列出全部依賴引用，含99副本（按§六開頭的分段換算逐行核對）、遊戲數據與ID名。
- [ ] 以章號命名的ID（`BR_CH`、`FLAG_MAIN_CH`、`PROMISE_CH` 等）改用新的正式章號，回收章欄一併更新；同一提交完成。

**修改總綱09或設03、設11、設12、設13時**：把同一處修改套用到99的對應行（換算見§六開頭；09:1–9 為＋840、09:10起為＋848），不得整段覆蓋99的副本。
